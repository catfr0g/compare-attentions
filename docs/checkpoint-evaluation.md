# Оценка сохранённого чекпоинта

Команда `eval` считает loss и точность на существующем разбиении датасета. Она не обучает модель, не создаёт датасет и не отправляет данные в ClearML или Hugging Face.

## Запуск

Из корня проекта:

```bash
uv run eval --checkpoint /path/to/model.pt --data /path/to/dataset --split test --batch-size 32 --device cuda --dtype float16 --output local/reports/test-eval.json
```

Альтернативный вход:

```bash
uv run python -m compare_attention.cli.evaluate --checkpoint /path/to/model.pt --data /path/to/dataset
```

`test` — значение `--split` по умолчанию. Допустимы также `val` и `train`; отсутствие выбранных файлов вызывает ошибку, а не переключение на другое разбиение. Родительский каталог для `--output` должен существовать. Существующий файл не перезаписывается. Без `--output` JSON выводится только в stdout.

## Форматы чекпоинта

- `model.pt` с FP32 state dict и соседним `run_identity.json`. Архитектура берётся из identity; fingerprint весов должен совпадать с `final_parameters_sha256`.
- Каталог результата: команда читает его `model.pt`.
- Отдельный FP32 state dict без identity: укажите `--config training.yaml` с полным разделом `model`. Если identity существует, явно переданный model config должен с ним совпадать.
- Полный checkpoint `step_XXXXXXXX.pt` либо указатель `latest.json` из каталога `checkpoints`. Проверяется встроенная целостность, а для указателя — относительный путь и SHA256. Используются только веса и конфигурация. Optimizer, scaler, сохранённые RNG и счётчики обучения не восстанавливаются.

Перед загрузкой проверяются ключи, формы, FP32 dtype, конечность тензоров и согласованность связанных параметров, в том числе `wte.weight` / `lm_head.weight`. `torch.load` работает с `weights_only=True` и `map_location='cpu'`. Чекпоинты с FP16/BF16 параметрами эта версия не принимает; dtype прямого прохода настраивается отдельно.

## Устройство и точность вычислений

- `--device auto`: CUDA, если она доступна, иначе CPU.
- `--dtype auto`: FP16 autocast на CUDA; FP32 на CPU. Параметры остаются FP32.
- Явно доступны `float32`, `float16`, `bfloat16`; неподдерживаемое сочетание вызывает ошибку.
- С текущим DeltaNet backend нужен CUDA. CPU поддерживает classic/FP32; подмены DeltaNet другим backend нет.
- Внешняя компиляция выключена. Прямой проход выполняется с `model.eval()` и `torch.inference_mode()`.

Локальная оценка может выполняться на другой GPU и другой сборке Torch, чем обучение. JSON содержит фактический runtime; побитное совпадение с обучающим окружением не обещается.

## Метрики

Метки сравниваются с предсказаниями **на той же позиции**, без next-token shift. Позиции с `label=-1` исключаются. Loss — сумма NLL, делённая на число всех оцениваемых меток, а не среднее средних по batch. Последний неполный batch включается.

- `accuracy`: доля правильных ответов среди supervised позиций.
- `accuracy_percent`: та же доля в процентах.
- `correct`, `supervised_count`, `rows`: абсолютные количества.
- `loss`: средняя NLL на supervised позицию.
- `split`, `batch_size`, `device`, `inference_dtype`, `parameter_dtype`: режим оценки.
- `checkpoint`, `model_config`, `data`, `runtime`: конфигурация, provenance и SHA256 входных файлов.

Пустая выборка, отсутствие supervised меток, неверные формы/типы/диапазоны входов и меток, несовпадение с metadata, нечисловые logits или loss вызывают ошибку. Batch оценки не меняет batch уже завершённого обучения.

## Что означает K8

В нашей KV retrieval задаче `K` — количество пар «ключ → значение» в контексте одного примера. `K8` содержит восемь таких пар, `K64` — 64. Это не число слоёв, не размер модели и не batch size. Текущий K8 test split содержит 1000 примеров по восемь запросов: всего 8000 оцениваемых ответов. Accuracy считается по этим ответам, а не по условию «все ответы строки правильные».
