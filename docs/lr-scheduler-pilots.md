# LR и расписание: отдельные контролируемые пилоты

## Цель

Проверить отдельно величину learning rate и форму его изменения. Размер модели, общий batch 32, данные, seed 42, FP16 AMP/FP32 параметры, cap 128 и compilation остаются прежними. На каждый полный пилот выделено `10^16` алгоритмических FLOPs, early stopping выключен.

## Конфигурации

- `experiments/fp16_lr_pilots/1e-3/`: постоянный LR `0.001` — первый контроль.
- `experiments/fp16_lr_scheduler/1e-3/`: тот же peak LR `0.001`, warmup + cosine — отдельный фактор.
- `experiments/fp16_lr_pilots/1e-4/`: постоянный LR `0.0001`, только подготовлен; автоматически не запускается.

В каждой ветке есть `full`, `exact1`, `exact32` и отдельные YAML для classic/DeltaNet. Всего подготовлено 18 конфигураций. Данные и production source фиксируются в одном неизменяемом выпуске; подготовка не означает публикацию или запуск.

Новые параметры Optim:

```yaml
optim:
  learning_rate: 0.001
  weight_decay: 0.1
  lr_schedule: warmup_cosine
  warmup_fraction: 0.05
  min_lr_ratio: 0.1
```

`lr_schedule: constant` оставляет LR постоянным; это значение по умолчанию для старых YAML. Для scheduled-ветки `learning_rate` обозначает peak, не стартовый LR.

## Ось расписания

LR выбирается по прогрессу к концу очередного успешного обновления:

`p = min((completed_flops + step_flops) / train_flops_budget, 1)`.

До 5% бюджета LR растёт линейно до peak. Затем cosine decay снижает его к 10% peak при завершении бюджета. Перерасход последнего целого update ограничивает `p` единицей. Частота validation, checkpoints и вывод логов расписание не продвигают. Ошибка/пропущенное обновление не превращается в выполненный бюджет.

Exact1 и exact32 — проверки соответствующих коротких конфигов, а не префиксы полного LR-профиля: их бюджет намеренно короче, поэтому расписание сжато на свой горизонт. Они проверяют реализацию/границы и численную устойчивость на этом горизонте, не доказывают устойчивость всего полного прогона.

## Наблюдаемость и resume

Для scheduled-ветки фактический LR после каждого успешного update записывается в `metrics.jsonl` как `type: learning_rate`, в читаемый train.log и в ClearML. Snapshot содержит полный config, фактический LR optimizer и выполненный FLOPs-прогресс; отдельного изменяемого счётчика scheduler нет.

При resume LR следующего обновления выводится из сохранённого прогресса. История LR переносится вместе с loss/validation, RNG восстанавливается после callbacks. Старые snapshots с неполным относительно нового config набором Optim-полей не объявляются автоматически совместимыми: полное равенство научного config остаётся обязательным.

## Протокол допуска

1. Полная регрессия и независимая проверка нового source.
2. Для постоянного LR `1e-3`: classic exact1 → gate → DeltaNet exact1 → gate → classic exact32 → gate → DeltaNet exact32 → gate → два полных пилота с проверкой каждого до следующего.
3. Такой же порядок для warmup/cosine с тем же peak LR.
4. Остановка для анализа; LR `1e-4`, новые B8 и DDP автоматически не запускаются.

У каждого результата проверяются фактический runtime, исходные tensor fingerprints, конфигурация/данные, реальные updates, конечная история, checkpoints и фактическая последовательность LR. При смене runtime Kaggle результат не считается matched-сравнением и очередь останавливается. Это проверка фактического окружения, не обещание установки фиксированного Kaggle image.

Результаты scheduler сопоставляются с постоянным LR того же peak и бюджета. Прежний B32/LR `3e-4` используется как отдельная исходная точка только при совпадении runtime и остальных согласованных настроек. Один seed — исследовательский пилот, не окончательный выбор оптимального LR.
